# 黑房弹球：朋友联机对战设计

日期：2026-10-12

## 目标与范围

在 Muwei-TA/blackroom_Bonk.io 空仓库中开发一款 Bonk.io 风格的浏览器物理竞技游戏，使用原创名称、画面和地图。朋友通过房间码进行 2–8 人对战，电脑键盘操作，无需账号。支持 Docker Compose 部署，并用 Git 保存阶段性开发记录。

首版不包含公开匹配、排行榜、账号系统、聊天、自定义地图、移动端触控或跨实例房间同步。昵称、房间及比分仅驻留服务器内存，服务器重启后清空。

## 用户流程

1. 首页输入昵称，创建房间或输入房间码加入。
2. 房间展示房间码、玩家列表、房主和操作说明；房主选择三张地图之一。
3. 所有人默认可参赛，房主在至少两人时开始比赛；准备页不另设准备按钮。等待中的房间可加入，比赛中的房间拒绝新玩家。
4. 每轮开始前倒计时三秒，玩家从地图预设的不重叠位置出生；比赛开始后锁定地图。
5. 玩家操控圆球，相互碰撞，将对手挤出场地；存活到最后者赢得一分。先赢五轮者赢得比赛。
6. 展示比赛结果，房主可返回准备页重开，保留仍在线的玩家并清空比分。

## 操作与物理规则

- A/D 或左右方向键水平移动，W 或上方向键跳跃，仅接触可站立表面时允许跳跃；S 和下方向键不产生额外动作。
- 按住空格进入加重状态，提高质量和抗撞能力，同时降低移动加速度；释放恢复普通状态。
- 服务端使用 Matter.js，固定 60 Hz 更新物理世界；客户端仅发送按键状态，不能提交位置、速度或比分。
- 地图包含静态平台、斜坡和掉落区域，三张地图分别突出宽平台、阶梯平台和倾斜平台。每张地图都有八个有效出生点和明确淘汰边界。
- 玩家超出地图淘汰边界后，本轮不能再施加输入；镜头展示整个竞技场，淘汰者可继续观看。
- 单轮最多 90 秒。剩余一人时该玩家得一分；同一物理步全部淘汰或时间耗尽仍剩多人时记平局，无人得分。结算停留三秒后开始下一轮。
- 比赛过程中人数少于两人时终止比赛并返回准备页，提示原因，清空比赛比分，避免自动刷分。
- 页面失焦或隐藏时清空按键，服务端对超过一秒没有更新的输入清零。物理参数集中定义，验收重点为可操控性、有效碰撞、稳定落地和加重效果。

## 技术方案与边界

选择 TypeScript、Node.js、WebSocket、Matter.js 和浏览器 Canvas。Vite 负责前端开发及打包，生产环境由 Node.js 同源提供静态页面和 WebSocket，避免多服务部署。

模块职责：

- 共享协议：消息类型、房间状态、输入结构和公共常量，不依赖浏览器或服务器运行环境。
- 地图定义：平台几何、出生点和淘汰边界，供服务器创建物理世界及客户端绘制。
- 物理模拟：碰撞、输入、落地检测、加重和淘汰，不负责网络连接。
- 房间与比赛：玩家成员关系、房主权限、状态切换、回合和比分，不直接操作 DOM。
- 网络服务：连接、消息校验、房间路由、心跳与广播。
- 浏览器客户端：大厅和房间界面、输入采集、状态插值、Canvas 绘制及比分展示。

服务器每秒广播 20 次世界快照，包含单调递增的序号、时间、玩家位置和比赛状态。客户端按接收快照进行插值；首版不实现客户端预测或回滚。房间事件即时广播。输入以固定频率更新并包含序号，旧输入丢弃。每个房间独立模拟，不共享实体或比分。

客户端通过 HTTP 获取页面和静态资源，通过同源 `/ws` 建立连接。生产 HTTPS 部署自动使用 WSS。连接身份由服务器生成并绑定到连接，玩家不能通过消息冒用其他玩家。

## 房间、异常与资源限制

- 房间码使用六位不易混淆的大写字母和数字，生成时检查重复，不承担账号认证功能。
- 昵称去除首尾空白，限制为 1–20 个字符，按纯文本显示；同房间允许重名，通过玩家 ID 和颜色区分。
- 房间最多八人，服务器默认最多一百个活跃房间；达到容量时返回清晰错误。
- 校验消息类型、字段、数值范围及当前状态；限制消息大小为 4 KiB、每连接每秒最多 60 条应用消息。无效操作不能改变比赛状态，持续超限者断开。
- 错误涵盖无效昵称、无效房间码、房间不存在、满员、正在比赛、非房主操作及人数不足。客户端显示可读中文提示。
- 一个连接同时仅属于一个房间，离开时清理成员和实体，空房间立即销毁并停止计时器。
- 主动离开或确认断线后移除玩家；房主移交给最早加入的剩余玩家。比赛中的离线玩家视为淘汰，并重新评估回合和参赛人数。
- 使用 WebSocket ping/pong 检测失联连接，最长约 30 秒清理。客户端断线后显示提示并提供返回首页入口；首版不恢复原有身份或比分。

## 开发、Docker 与运行配置

- 固定 Node.js 22 大版本，提交 npm 锁文件，安装使用 `npm ci`。提供开发、构建、类型检查、测试和生产启动命令。
- 开发模式运行 Vite 与后端，Vite 代理 `/ws` 和 `/healthz`；生产模式单个 Node.js 进程监听 `0.0.0.0`。
- 多阶段 Dockerfile 完成依赖安装、构建和生产依赖裁剪；运行镜像使用非 root 用户。Compose 默认将宿主机 3000 端口映射到应用，包含健康检查和重启策略。
- 默认端口为 3000，可通过 `PORT` 配置；提供 `.env.example`，不提交密钥、依赖目录或构建产物。本项目默认不需要外部服务或凭据。
- `/healthz` 返回 HTTP 200 和 JSON 服务状态；SIGTERM 时停止接受连接、关闭 WebSocket 并释放物理模拟计时器。
- README 包含本地开发、键位、游戏规则、测试、Docker Compose 部署和故障排查。公网部署使用支持 WebSocket 的 HTTPS 反向代理，单实例运行；端口或证书配置属于部署方责任。
- 云任务复用当前隔离环境和检出目录，不另建 Git worktree。完成后保存经过验证的云环境安装及启动说明；进程不作为可恢复快照的一部分。

## 验收与验证

1. 自动测试物理输入、落地跳跃、加重状态切换、掉落淘汰、平局、得分、五分获胜和人数不足终止。
2. 自动测试加入限制、房主权限、房主移交、空房间销毁、非法消息与输入序号处理。
3. 使用真实 WebSocket 客户端进行至少两人的完整联机冒烟测试，覆盖创建加入、开始、输入、快照、计分、断线和两个房间互不影响。
4. 运行类型检查、自动测试和生产构建，启动生产服务验证静态页面、健康检查及 WebSocket 路径。
5. 使用浏览器验证两个客户端进入同房间、实际操作、中文界面及错误提示；确认没有未处理的控制台错误。
6. 构建 Docker 镜像并通过 Compose 启动，验证容器健康检查与双客户端联机；若云环境缺少 Docker 能力，明确报告未执行的容器验证，不以本地 Node.js 成功代替。
